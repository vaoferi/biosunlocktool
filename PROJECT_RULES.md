# PROJECT_RULES.md — BIOS Unlock Tool (Cloudflare Pages)

Тут лише факти та інваріанти цього репозиторія. Універсальний контракт агента
живе в канонічному `AGENTS.md`, який постачає Start Here sync; у частині фактів
цього репо цей файл має пріоритет.

## Що це за проєкт

`biosunlocktool` — це поверхня публікації Cloudflare Pages для лендінга BIOS
Unlock Tool. Один Pages-проєкт `biosunlocktool`, вісім host-ів: apex, `www`,
`us`, `ca`, `in`, `pl`, `de`, `af`. Мовні версії — не технічні копії, а окремі
версії сайту для ринку; деталі й таблиця — `docs/market-routing.md`.

Стек: чисті `HTML` + `CSS` + `JS` і одна Pages Function
`functions/_middleware.ts`. `build.js` навмисно тривіальний — він тільки
повідомляє про готовість локалей, це не компілятор і не бандлер. Немає
framework, TypeScript-збірки, bundle-кроку чи Node runtime у продакшні.

## Джерело істини для лендінга

Канонічний текст і ассети англійського лендінга живуть НЕ тут, а в
`vaoferi/nexxgsm-design`, директорія `versions/en-US-landing/`. Напрям
підтверджений байтами, а не словами: на коміті `52bdbbe` файли
`index.html` (`f5f230e1beb8`) і `assets/css/main.css` (`5fcbbe1b0e45`) у
NexxGSM і в корені цього репо однакові, а коміт NexxGSM на хвилину раніший за
коміт, який заніс їх сюди.

Практичний наслідок: правку видимого лендінга спочатку інтегрують у NexxGSM
canonical, потім копіюють у цей репо. Якщо зміна зʼявилася лише тут — це
випадковий форк, і його треба вернути в canonical, а не тиражувати.

## Контракт дзеркала root ↔ locales/en-US

Англійський лендінг публікується двома шляхами: з кореня репо і з
`locales/en-US/`. Це два способи подання одного документа, тому відповідні
файли мають бути байт-тотожні. Ворітка —
`npm run check` (`scripts/check-surface-parity.mjs`), вона падає на будь-якій
розбіжності й на відсутній копії. Виміряний приклад дефекту, який вона ловить:
до появи ворітки `locales/en-US/assets/js/india-language.js` відстав від
кореневого і втратив два DOM-хуки (`sectionTitle` і `label`).

`locales/de-DE/`, `locales/pl-PL/`, `locales/af-ZA/` — окремі мовні документи
(по одному `index.html`), вони не дублюють ассети, а посилаються на спільні
`/assets/*` з кореня. Для них вимога тотожності не діє; для них діяє вимога
оновити cache stamp у кожному HTML після зміни спільного CSS.

## Маршрутизація

`de`, `pl`, `af` отримують внутрішній `ASSETS.fetch` на
`/locales/<locale>/` із trailing slash, тож чистий URL субдомену зберігається.
`ca` і `in` свідомо проходять до спільного кореня, де тема ринку вибирається
через `data-market`. Точні legacy-шляхи `/locales/<locale>` і
`/locales/<locale>/index.html` отримують `301` на чистий root свого
субдомену; ассети та інші шляхи не переписуються. `locales/en-IN/` — legacy
Hindi stub, він не маршрутизується.

Поведінка закріплена тестами `tests/routing.test.mjs`, які викликають
справжню функцію `onRequest` з підставним Pages context.

## Build, тести й локальна перевірка

Усе виконується на NAS Linux у canonical checkout
(`/volume1/homes/vaoferi/Work/8fc8/biosunlocktool`):

```bash
npm install      # локальний інструмент для перевірки, не часть публікації
npm run build    # node build.js
npm run check    # ворітка дзеркала + node --test tests/*.test.mjs
npx wrangler pages dev . --local --ip 127.0.0.1 --port 8788
```

Виміряне середовище 2026-09-25: Node `v22.23.3`, npm `10.9.9`,
`wrangler` фактично `3.114.17` при заявленому `^3.90.0` у `package.json`.
Локфайла в репо немає, тому версію треба міряти, а не виводити з діапазону.

Обмеження локального runtime: `pages dev` віддає fallback на `index.html` для
неіснуючих шляхів (`/robots.txt` у репо немає, і локально він повертає 200 з
розміром головної сторінки), а `301` формує з схемою `http`, бо локальний
сервер слугає HTTP. Тож статус неіснуючого шляху і схема редиректу в проді
локально не доводяться — це окрема перевірка після релізу.

## Публікація й повноваження

Реліз робить GitHub Actions `.github/workflows/deploy.yml`: він запускається на
push у `main` і через `workflow_dispatch`, і виконує
`wrangler pages deploy . --project-name biosunlocktool`. Тобто пуш у `main` —
це продакшн-дія.

- Зміну, чия мета — продакшн, не зливати в `main` без явної команди
  власника. Готовність джерела і факт деплою — різні речі.
- Секрети `CF_ACCOUNT_ID` і `CF_API_TOKEN` живуть у repository secrets; значення
  не потрапляють у репо, логи чи документацію.
- Історичний факт стану: на 2026-09-11 локальна автентифікація Wrangler і прямий
  Pages deploy працювали, а останні GitHub Actions завершувалися помилкою
  Cloudflare API `10000` (недостатні права секрету). Повторними спробами це не
  маскується.

## Робоча станція

macOS чи Windows — редактор, SSH-клієнт і браузер. `npm install`,
`node build.js`, локальний Pages runtime і ручна синхронізація ассетів на
станції не є підтримуваним шляхом. Історичні обхідні шляхи для Windows
(mapped drive замість UNC) лишаються лише нотаткою для діагностики: причина
була в запуску збірки на станції.

## Приймання

- HTTP 200 і `curl` не є доказом готовності UI: потрібен реальний браузер.
- Перевіряти фактичний DOM/runtime: `lang`, копія hero, тема фону відповідають
  host; India toggle перемикає English ↔ Hindi без зміни URL і canonical;
  legacy-шлях дає `301` на чистий root; горизонтального overflow нуль;
  критичних console errors нуль; mojibake нуль; cache stamp спільного CSS
  оновлений в усіх landing HTML.
- `canonical` і `og:url` навмисно вказують на `https://biosunlocktool.com/`;
  субдомени — точки входу ринку, а не окремі SEO-канонікали.
